## 0. ГЛАВНЫЙ ТЕЗИС (чем это оказалось)

Облако — не «набор эвристик с растеканием». Это **рекурсивный байесовский фильтр** (recursive Bayes /
histogram filter) на графе навмеша. `belief(x) = P(игрок в ноде x | вся история наблюдений)`. Все
разрозненные правила §LKP (свежее бьёт старое, слияние конусов, стекание в проёмы, методичная
зачистка) **выводятся из одного закона**, а не дизайнятся по отдельности. Это и есть искомый «гарант»:
не «навесили правил и надеемся», а «есть закон, из которого правила следуют». Дешёвый конус (K лучей ×
`vertex_in_direction`) — это **аппроксимация этого фильтра с двумя известными членами ошибки** (см. §5),
а не куча надежд.

## 1. ЗАКОН В ДВЕ СТРОКИ (predict / update)

Belief живёт циклом из двух чередующихся шагов:

- **PREDICT** (прошло время, наблюдений нет): `b'(x) = Σ_x'  T(x|x') · b(x')`.
  T = переходное ядро («куда игрок мог перейти из x'»). Вера растекается. **Энтропия растёт.**
  → это «стекается» / «конус расширяется со временем».
- **UPDATE** (пришло наблюдение z): `b(x) ∝ P(z|x) · b'(x)`, затем ренормировка.
  Наблюдение переформовывает веру. **Энтропия падает.**

Всё остальное — следствия. Три «допущения энтропии» из §LKP схлопываются:

- **«свежее бьёт старое»** — НЕ правило. Старая инфа прошла много predict-шагов → размазана тонко →
  вкладывается слабо. Свежая = резкий спайк из update. Никакого `if свежее`. Само.
- **«близко усреднить / далеко держать два конуса»** — НЕ два правила, а ОДНО умножение. Два
  свидетеля = две likelihood, перемноженные в веру. Совпали → произведение заостряется на пересечении
  («усреднить»). Разнесены → произведение **бимодально**, вера сама держит два горба («раскол
  внимания»). Раскол — **теорема** (произведение разнесённых likelihood многомодально), не спецкейс.
  Его нельзя предотвратить, он выпадает из закона.

## 2. PREDICT = ДИФФУЗИЯ = ГЕОДЕЗИЧЕСКИЙ ФРОНТ (не евклидов веер)

Predict-шаг на графе — это **уравнение теплопроводности на навмеше**. Вера растекается как тепло.

**Почему «стекает в проёмы» — теорема, а не везение:** тепло течёт через дверь, потому что дверь =
единственное ребро графа между двумя объёмами. Точки за стеной **геодезически далеко** (обойти через
дверь), хотя **евклидово рядом**. Поток веры физически обязан идти через бутылочное горло. В теории
графов это **Cheeger bottleneck** (узкое место проводимости); диффузия концентрируется на нём.
Спектральная геометрия, не удача.

**Отсюда — ключевой довесок сессии (упрочнение ядра, не фича):**
заменить евклидов тест «нода в растворе конуса» на **геодезический фронт через кэшированное поле
расстояний.**

- В момент нового LKP → один проход **Dijkstra** от ноды-источника по навмешу → поле `dist[node]` =
  геодезическое расстояние до каждой ноды. Кэшируется. Статично, пока нет нового наблюдения.
- Каждый тик зона поиска = `{ node : dist[node] ≤ v_max · age }`. **Ноль работы на тик** (сравнение
  чисел по кэшу). Фронт волны сам расширяется по времени, сам заворачивает за углы (dist считался по
  связности), сам концентрируется в дверях (геодезия).

**Инверсия, ради которой лезли вглубь:** правильный объект (геодезический wavefront) не только
корректнее евклидова веера (веер НЕ умеет завернуть за угол — луч упирается в стену, вера не втекает
в изогнутый коридор), но и **дешевле амортизированно**: один Dijkstra на смену LKP вместо K рейкастов
каждый кадр. Правильное оказалось и вернее, и дешевле хака.

**Бонус — убивает оконный geodesic-teleport (баг прошлой сессии):** евклидов снап off-mesh точки мог
посадить belief по ТУ сторону стены (евклидово рядом, геодезически бесконечно далеко). Геодезическое
поле по определению не может — ребра сквозь стену нет, dist через стену = ∞. Баг не «фиксится», он
**перестаёт быть выразимым** в этом представлении. Ср. §РАЗВЕДКА ⚠️ + v0.7-core snap_to_mesh.

**Реализация фронта — РЕШЕНО (вкус игрока):** растекание в РЕАЛЬНОМ ВРЕМЕНИ, инкрементально
(доращивать фронт по мере роста age), НЕ рывком на макс-радиус. Причина не только эстетика: negative
info (§3) выедает по КРАЮ растущей волны; живой фронт создаёт саму поверхность, по которой скребёт
резец. Рывок = нечего постепенно выедать. Растекание дёшево (арифметика по кэшу) → за FPS не страшно;
дорого только зрение-выедание (§3), его дозируют. NB: это Dijkstra с ранней остановкой по порогу
`v_max·age` (заливаем только достижимый пузырь), не полный по уровню. Инкрементальный Dijkstra —
вопрос к консоли/Фаблу.

**NB навигация ≠ растекание.** Dijkstra (ненаправленный, вширь) = РАСТЕКАНИЕ веры. A* (Dijkstra +
эвристика к цели, направленный) = НАВИГАЦИЯ бойца к выбранной зоне. Разные инструменты, не путать.
X-Ray pathfinder = A* в C++ (ванильная моторика к точке уже оптимальна — см. §4).

## 3. UPDATE ПО ОТРИЦАТЕЛЬНОМУ СВИДЕТЕЛЬСТВУ (сердце ядра, «щелчок»)

**Тезис:** позитив («вижу в X») редок и короток. Негатив («смотрю в X, пусто») идёт НЕПРЕРЫВНО, каждый
кадр, по всей площади обзора. Ваниль весь этот поток ВЫБРАСЫВАЕТ (умеет апдейтить только на позитиве) —
сливает 99% реально полученной сенсорики. Наше облако **слушает тишину**. Это не добавленный интеллект,
это **прекращение выброса данных**, которые и так есть. Отсюда ощущение «читерски-умное, не будучи
умным».

**Механика — НЕ зануляй в ноль, умножай на маленькое:**

    b(x) *= (1 − P_detect(x))

`P_detect(x)` = вероятность «я БЫ заметил игрока, если бы он был в x». Жёсткое `b(x)=0` = God-eyes
наоборот («смотрел → там ТОЧНО пусто»), тот же протагонист-байес, от которого бежим. Правильное «≈0»
через `P_detect` втекает одним множителем:

- дальняя нода → низкий P_detect → вера гаснет СЛАБО → остаётся сомнение → NPC вернётся перепроверить;
- ближняя, освещённая → высокий P_detect → гаснет почти в ноль → «в упор смотрел, пусто»;
- тень/дым/куст на ноде → низкий P_detect → вера **липнет к укрытиям** → NPC органически подозревает
  именно укрытия. Не потому что знает — потому что **не смог опровергнуть.** Игрок в тёмном углу
  ощущает, что его «чуют». Это `1−P_detect` на затенённых нодах, эмерджент, не скрипт.

**P_detect = ЛОГ-ЛИНЕЙНАЯ МОДЕЛЬ (формула калибровки):**

    P_detect = σ( w0 + w_dist·f(dist) + w_light·light + w_pose·pose + w_rank·rank + … )

где σ = сигмоида. Разрешает интуицию «наслаивание ≠ сложение и ≠ умножение»: ВНУТРИ (в log-odds) члены
**складываются** со своими весами `w`, СНАРУЖИ (после σ) выглядит как **умножение**. Сигмоида — мост
между двумя ощущениями. Синергия сохраняется при почленной калибровке: два слабых члена вместе
перепрыгивают порог σ, поодиночке нет (тень СДВИГАЕТ точку, где дистанция начинает кусаться). Калибруешь
`w` по одному — нелинейность скрещивает их бесплатно.

**Тактика калибровки:** слоёный пирог, НЕ почленно-последовательно. Начать со СКЕЛЕТА (чистая
дистанция, одна ручка → уже даёт «дальнее гасит слабо»), затем домешивать по одному члену (свет →
поза → …), каждый раз глядя на полигон. `P_detect` — **самый чувствительный параметр всей системы**
(см. §6 «камень раскалибровки»).

**Смерть цикла (исчерпание веры):** когда вся масса выедена ниже порога = «проверил всё достижимое,
нигде нет». Это не таймаут «забыл», а **вывод**: игрок вышел из контролируемой зоны. Правильная реакция
приходит в правильный момент (пространство исчерпано), не по произвольным 2с. Далее → give-up
(вернуться на пост, Грех-подобно) ИЛИ эскалация (расширить на соседние объёмы, звать своих через крик).

## 4. РАНГ = ДЕГРАДАЦИЯ ВОСПРИЯТИЯ/РЕШЕНИЯ, НИКОГДА МОТОРИКИ (принцип, LOCK)

**Правило:** деградацию плохого бойца вешаем на belief и выбор цели, НЕ на навигацию/прицел-код.
Кривая моторика = глюк на вид («ИИ сломался»). Кривое знание = характер («боец в панике»).

Ранг модулирует ДВЕ ортогональные оси, обе уже в ядре, перемножаются:

- **острота P_detect** (§3): мастер чисто выедает пространство с первого взгляда даже на дальних/тёмных
  нодах; новичок «смотрит», вера почти не гаснет → перепроверяет очищенное, суетится, паникует. Резец
  по belief туп.
- **горизонт lookahead** (infotaxis, §5): мастер планирует, КУДА резать, на ходы вперёд; новичок —
  myopic зашумлённый одношаговый.

Одна скалярная «ранг» → две способности. Признак правильной абстракции. Практический вывод для §7.6 и
гандикапа навигации: **новичок бежит тем же оптимальным A*, но в НЕПРАВИЛЬНУЮ ноду** (замусоренный
belief, гонится за фантомным пиком). НЕ давать новичку «худший алгоритм» (дорого + фальшивая glitchy
тупость). Навигация у всех одна оптимальная; тупит ВЫБОР ЦЕЛИ, а его качество уже завязано на ранг.

## 5. ПОЛИТИКА ПОИСКА = СПУСК ПО ЭНТРОПИИ (infotaxis)

Энтропия веры `H(b) = −Σ b(x)·log b(x)` — одно число, **логируемое** (растёт на predict, падает на
update; готовый прибор для полигона). Политика поиска: NPC выбирает действие, максимально снижающее
**ожидаемую** энтропию. «Проверить самый массивный непросмотренный угол» = жадный шаг по градиенту
информации. Имя: **infotaxis** (поиск по градиенту информации; так мотыльки идут на феромон в
турбулентности с рваным сигналом). Поиск = спуск по энтропии, не скриптовый sweep.

**Цикл без залипания (важно):** после выедания НЕ «возврат к исходной точке LKP» (она уже опровергнута,
там был, пусто → стереть свою работу, зациклиться). Правильно — **перецелиться на текущий пик
остаточной веры** (максимум непроверенной массы). Это и есть infotaxis-шаг; не даёт зациклиться by
construction (пик монотонно смещается от вычищенного к невычищенному).

**Замыкание петли (active perception, вылезет в 1-й час плейтеста):** как только NPC ДВИЖЕТСЯ по
belief — движение меняет что он видит → меняет belief. Петля обратной связи. Может стабилизировать
(пошёл на пик → добрал инфы → заострил), может **залипнуть** (закоммитился в фантом → пошёл ОТ игрока →
корректирующего наблюдения нет → уверенно неправ). Лечение: событие «ждал контакт — не получил» должно
**взрывать неопределённость** (по Байесу: P(нет контакта | игрок тут) мало → постериор прыгает). Конусу
нужен триггер ре-расширения + пол, ниже которого не сжимается.

## 6. ГДЕ УКУСИТ (честная узда — три камня, все = ОДИН параметр P_detect)

- **Камень раскалибровки.** P_detect — сердцебиение системы. Задрал → мгновенное вычищение, God-eyes,
  укрытия не работают, смысл убит. Занизил → вера не гаснет, вечная суета по проверенному, слепой идиот.
  Между обрывами — узкая тропа, калибруется ЭМПИРИЧЕСКИ на полигоне, не на бумаге. Первый заход даст
  терминатора ИЛИ слепого — это норма, крутишь одну ручку.
- **Камень стоимости (ответ на «не посадит ли FPS»).** Negative update требует знать, какие ноды NPC
  видит СЕЙЧАС = LOF-рейкасты, единственный дорогой расход (§ПРОИЗВОДИТЕЛЬНОСТЬ). Наивно (рейкаст в
  каждую ноду фронта каждый тик) = смерть FPS. Спасение: **растекание и выедание НЕ на одной частоте.**
  Фронт растекается каждый тик (дёшево, арифметика по кэшу dist). Зрение-выедание идёт БЮДЖЕТОМ:
  time-slicing (N нод за кадр), кэш видимости на нодах с ленивым обновлением, дои движковый
  `memory_visible_objects` вместо своих рейкастов где можно. То же, что дало гладкие 15×15 (с8).
- **Камень ложной уверенности.** Высокий P_detect на затенённых нодах → NPC вычистит укрытие, где
  игрок реально сидит, и уйдёт уверенно неправым. Обратная сторона «чуйки на укрытия». МОЖЕТ быть
  ФИЧЕЙ (эмерджентный стелс: замри в тени, патруль пройдёт мимо) — но только как СЛЕДСТВИЕ честного
  низкого P_detect в тени, не случайный артефакт. Грань «эмерджентный стелс / слепой баг» = снова
  калибровка P_detect.

**Вывод:** вся мощь и весь риск ядра сжаты в ОДНУ скалярную функцию P_detect. Не конус, не Dijkstra —
вот эта «вероятность что я бы заметил». Честно отформулируешь → чуйка на укрытия + ранговая
дифференциация + эмерджентный стелс + правильный момент «потерял». Схалтуришь → терминатор/слепой.
Ядро знает, куда смотреть.

## 7. КОМАНДНЫЙ ЦЕНТР — ЭМЕРДЖЕНТ ИЗ РАЗБРОСА РАНГОВ (снимает развилку §НАБЛ 7.6)

Контекст: §7.6 ставила развилку «ветеран в атаке = жёсткий танк (7.5) ИЛИ командир (новички как мясо)»,
помечена «выбор = дизайн-развилка звена 4, пока не трогать». **Развилка снята: это не или-или, обе роли
— одна формула ранговой разницы на разных входах.**

- **Абсолютный ранг** ветерана → НАСКОЛЬКО он смещается от «мяса».
- **Разница** между ним и остальными → В КАКУЮ из двух ролей смещение выливается:
  - ветеран среди новичков (большая разница вниз) → рационально беречь себя, тратить их → **командир**
    (сам сзади, distributed-решение через него, новички = сенсоры/приманки);
  - ветеран среди равных/крепких (малая разница) → некого назначить мясом, каждый ценен → **сам в
    танк** (7.5, прёт под слабым огнём).

Состав заспавненного отряда ВЫБИРАЕТ роль сам через формулу. 4 ветерана → 4 танка без иерархии (некому
командовать). 1 мастер + 3 новичка → командир-с-мясом. Это §ФРАКЦИОННАЯ ГРАММАТИКА, только настройка =
распределение рангов ВНУТРИ отряда, а не фракция. **ИИГ-почкование (VARKA: порог `ранг×экип×оружие` →
раскол на coord-контексты) — тот же механизм; 7.6 = его частный случай.**

**Почему командный центр НЕОБХОДИМ (не «ещё фича»):** одиночная дедукция эксплойтабельна. Любое
поведение, сходящееся в детерминированную точку, НЕ зависящую от действий игрока, — заучиваемо (это
нарушение своего же принципа §7.3/§LKP «нельзя выучить позицию, зависящую от твоих действий» →
гарантированный эксплойт, не «может быть»). Partial observability + требование неэксплойтабельности
ЛОГИЧЕСКИ ВЫНУЖДАЮТ распределять сомнение, а распределять может только надстройка над бойцом.
Централизованное знание + децентрализованное действие (§АРХИТЕКТУРА «одно облако — разные планы») =
**структурный иммунитет к point-эксплойтам.** Дошли до центра СНИЗУ (от механики облака), не сверху
(«хочу спецназ»).

**Три ограничителя реализации (когда дойдём):**
1. **Гистерезис вместо пересчёта каждый тик.** Динамический выбор лидера без инерции = МИГАНИЕ (два
   близких ранга флапают → отряд дёргается; классич. leader-election flapping). Центр назначается с
   ЗАПАСОМ (перерасти на заметную дельту, не эпсилон) и НЕ переназначается, пока действующий жив/в
   строю. Смена только на смерть/разрыв связи/обвал. = §VARKA «ресурс-кулдаун ролей»: центр = роль с
   высоким кулдауном. **Удерживай лидера, не пересчитывай.**
2. **АУДИТ конфликта с ванильным `commander_id`** (флагнуто в 7-й точке §РАЗВЕДКА-мышления). Ванильная
   капитанская логика (`sim_squad_scripted`, `commander_id()`) висит на ALife/offline (кто ведёт по
   game-graph). Наш боевой центр = online-тактика в пузыре. ГИПОТЕЗА (под аудит, не факт): они
   ортогональны → вешать СВОИМ полем на squad-таблицу (`varka_combat_lead`), ванильный `commander_id`
   НЕ перезаписывать, максимум ЧИТАТЬ как дефолтный сид/tie-breaker («ранги равны → центр = ванильный
   командир»). Консоль: грепнуть кто читает/пишет commander_id, дёргается ли в бою.
3. **Ресурс РАНЬШЕ центра (ловушка порядка).** НЕ начинать с формулы выбора центра (это room-graph
   прошлой сессии — соблазнительная верхушка без фундамента). Центр, которому некем командовать,
   бесполезен. Сперва ОДИН распределяемый ресурс на squad-таблице (напр. остаточная belief-масса,
   разбитая на K зон → боец=зона), ПОТОМ надстройка «кто делит». Центр = функция над существующим общим
   ресурсом, не первый кирпич.

**Возврат к last-contact при смерти цикла (дедуктивная интуиция «след простыл — вернусь где точно был»)
+ его эксплойт-защита через центр:** соблазн вернуться в ТОЧКУ last-contact = fundament эксплойта
(игрок учит: толпа стечётся предсказуемо → куст + заготовленная граната → фарм). Защита (по возрастанию
элегантности): (1) не точка, а слабый широкий конус belief вокруг last-contact → веер вместо толкучки;
(2) negative info ПОМНИТ — вычищенные ноды восстанавливают веру со временем, не мгновенно → 2-й заход не
повторяет 1-й; (3) ГЛАВНОЕ — центр РАЗНОСИТ остаточное сомнение: не все в last-contact, а один держит
точку (приманка), двое перекрывают ПУТИ ОТХОДА из вычищенной зоны, один резерв. Эксплойтер ждёт толпу —
приходит перекрытие выходов, граната бьёт одного. Эксплойт умирает потому, что distributed-решение НЕ
сходится в точку by construction.

## 8. КРИК = ТРАНСПОРТНЫЙ СЛОЙ BELIEF (веха, встаёт МЕЖДУ одиночкой и центром)

Два слоя, НЕ смешивать:
- **фронтенд** (звук игроку) — косметика, дёшево: сыграть «Вон он!»/«Потерял!»/«Обходи!» в момент
  belief-события. Сам по себе пуст. = F.E.A.R. barks, но у Monolith заскриптованы (фейк без бэкенда).
- **бэкенд** (ради чего «рабочий механизм») — **распространение belief по слуху между NPC.** Наблюдение
  ОДНОГО бойца → слуховое событие (`memory_sound_objects`, §РАЗВЕДКА) → апдейт облака СОСЕДЕЙ, не
  видевших игрока. Превращает N одиночных наблюдателей в ОДИН распределённый.

**Щелчок:** крик несёт и НЕГАТИВ. «Чисто!»/«Пусто!» = распространяемое отрицательное свидетельство →
сосед вычищает угол в СВОЁМ облаке, не ходя туда. Отряд делит выедание пространства через звук; никто
не проверяет дважды прокричанное «чисто». → прямой мост к центру: центр ДИРИЖИРУЕТ этим («ты кричишь
что проверил — я разношу зоны по остаточной вере»). Крик = шина синхронизации belief; без него центр
глух.

**Очередь:** крик встаёт ПОСЛЕ первого одиночного потребителя (нужен работающий одиночный belief, чтобы
было что распространять) и ПЕРЕД командным центром (центру нужна звуковая шина как предпосылка). Ценность
крика НЕ в звуке (звук — бесплатный бонус + «несущая интеллекта» по Orkin'у: панель новичка / структурная
тишина наёмников), а в распределённом наблюдателе.

## 9. ОЧЕРЁДЬ (порядок вытекает из зависимостей, не из вкуса)

1. **Одиночный потребитель облака ДЕЙСТВУЕТ** — сегодняшний следующий шаг. Взгляд (`set_sight` в
   центроид/конус, контур едва замыкается, риск косметический) ИЛИ движение/пасинг к нодам конуса
   (контур замыкается жёстко, вся динамика залипания §5 включается сразу). РАЗВИЛКА ВЕЧЕРА: от выбора
   зависит, за чем смотреть в 1-м заходе. NB: полигоны пока плоские «пострелять/попрятаться», сложной
   позиционки/окон не было → оконный geodesic-teleport (§2) в логах ещё не всплывал; спросить консоль
   про снап off-mesh (euclid-ближайшая vs геодезически-достижимая в той же связной компоненте).
2. **Геодезический фронт** (§2) — упрочнение ядра: euclid-конус → Dijkstra-поле dist, инкрементальный
   реалтайм. Покупает door-concentration как ГАРАНТИЮ + убивает оконный teleport как КЛАСС + дешевле на
   тик. Веса пока не трогаем (остаёмся параметрическими, не полный байес-фильтр).
3. **Negative-info выедание** (§3) — b*=(1−P_detect), P_detect как лог-линейка, скелет = чистая
   дистанция, слоями. Time-slicing зрения (§6). Логировать H(b) (§5).
4. **Крик — транспорт belief** (§8) — соединяет одиночек звуком.
5. **Командный центр** (§7) — надстройка: ресурс раньше центра, гистерезис, аудит commander_id.

Мораль/усталость (заявлены игроком после стресс-теста, §журнал с8) — ось поведения поверх, дом ближе к
звену 2. НЕ здесь.

## 10. ЧЕТЫРЕ ЛОВУШКИ (аудит консоли 03.07: сверка теории с движком и живым кодом v0.7-core)

Найдены при вычитке этого файла против `varka_lkp.script` и распакованных оригиналов. Ничего
фатального, но каждая укусит, если не закрыть ДО кода соответствующего звена очереди §9.

**Л1. Ренормировка убивает «смерть цикла» — внутреннее противоречие §1 vs §3. [закрыть на бумаге
ДО звена 3]** §1 требует ренормировку после update (Σb = 1 всегда). §3 объявляет смерть цикла как
«вся масса выедена ниже порога». Несовместимо: если ренормировать после каждого негативного апдейта,
суммарная масса вечно = 1, порог недостижим, цикл бессмертен. Разрешение: ренормировать ТОЛЬКО на
позитиве; на негативе общей массе дать честно таять — тающая Σb и есть отдельная величина «насколько
я вообще верю, что он ещё в зоне». Смерть цикла = Σb < порог. Плюс страховочный кап по времени: при
низком P_detect везде (ночь) Σb асимптотит и порога может не достичь — «произвольные 2с» возвращаются
как задний предохранитель, просто сильно длиннее.

**Л2. Триггер пересчёта Dijkstra-поля: «на смену LKP» столкнётся с живым кодом. [звено 2]**
В `varka_lkp.script` пока NPC ВИДИТ врага, `mem_raw` свежеет каждый срез и `b.stamp = now`
непрерывно — LKP ползёт за живым контактом. Наивное «новый LKP → новый Dijkstra» = пересчёт поля
2 раза/с весь бой. Правильный триггер — ПЕРЕХОД видел→потерял (крючок готов: `last_seen` уже
трекается в npc_update); пока видит — точки достаточно, поле не нужно.

**Л3. Пик остаточной веры × бимодальность = мигание цели. [звено 3, принцип из §7.1]**
Два горба близкой массы (§1, теорема) + infotaxis «перецелься на текущий пик» (§5) = флаппинг:
выел чуть тут → пик перескочил туда → побежал → пик перескочил обратно. Та же болезнь, что
leader-election flapping, то же лекарство: ГИСТЕРЕЗИС — пик переназначается только при заметной
дельте массы, не при эпсилон. «Удерживай, не пересчитывай» (§7.1) — общий принцип ядра, не
спецправило центра.

**Л4. Облако УЖЕ отрядное → бэкенд крика внутри отряда пуст. [развилка, решить ДО звена 4]**
В v0.7 belief ключуется по `squad.id`: внутриотрядная телепатия мгновенна и бесплатна уже сейчас —
даже слишком честная. Крик как «шина синхронизации» (§8) внутри отряда ничего не добавляет:
синхронизация уже абсолютная. Развилка: (а) облако становится ПЕР-NPC (честно; крик = настоящий
транспорт слияния; дороже — N облаков) ИЛИ (б) облако остаётся отрядным, крик работает только
МЕЖДУ отрядами + как ОГРАНИЧИТЕЛЬ (дальность слышимости = радиус телепатии; вне слышимости отряд
рассинхронизирован). Выбор определяет, что такое «одиночный наблюдатель» вообще. Не решать сегодня,
но §8 без этого решения не стартует.

**Данные движка (проверено по `_unpacked`, не гипотезы):**
- Соседей ноды Lua НЕ отдаёт → Dijkstra через открытие соседей запросами `vertex_id` по сетке
  ~0.7 м (4 или 8 связность — вопрос консоли). Пузырь 30 м ≈ 5-6 тыс. нод ≈ ~20 тыс. вызовов:
  одним кадром — смерть FPS, инкрементально (§2 реалтайм-фронт) — незаметно. Живой фронт =
  условие выживания механики, не только вкус.
- `ray_pick` не используется НИ в одном ванильном скрипте → наличие в Lua Anomaly 1.5.3
  подтвердить консолью ДО проектирования выедания вокруг рейкастов. NB: `vertex_in_direction` =
  ПРОХОДИМОСТЬ, не видимость (ящик режет взгляд, но не навмеш; окно — наоборот). Для выедания
  навмеш-прокси не годится: NPC «вычистит» ноды за ящиками, которых не видел.
- `luminocity` движок считает ТОЛЬКО для актора и сам передаёт в `get_visible_value`
  (`visual_memory_manager.script:7`). API «свет на произвольной ноде» НЕТ → пер-нодовая тень
  («липнет к тёмным углам», §3/§6) в v1 недоступна честно. Костыль v1: luminocity актора как
  глобальный множитель (день/ночь работает, «тот самый тёмный угол» — нет). Записано, чтобы не
  было сюрприза «где мой стелс».
