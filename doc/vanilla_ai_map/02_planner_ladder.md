# 02 — Планнер: как NPC выбирает, что делать

У NPC нет «главного мозга с if-ами». У него **GOAP-планнер** (`motivation_action_manager`).
Это как диспетчер: смотрит на текущее состояние мира (набор флагов) и включает **одно**
действие с наивысшим приоритетом, чьи условия выполнены.

---

## World-properties — флаги-переключатели

Планнер читает мир как набор булевых флажков. Подтверждено грепом (`stalker_ids.property_*`):

```
   property_enemy              есть ли best_enemy (враг в памяти)?
   property_pure_enemy         враг «чистый» (реальный бой, не просто danger)?
   property_danger             есть угроза (граната/труп/удар из ниоткуда)?
   property_danger_grenade     конкретно рядом граната?
   property_alive              жив?
   property_critically_wounded смертельно ранен?
   property_items              есть предмет для подбора?
   property_inside_anomaly     стоит в аномалии?
```

Действия объявляют **preconditions** (какие флаги нужны) и **effects** (какие флаги меняет).
Планнер строит цепочку от «что есть» к «цель» и запускает первый шаг.

---

## Лестница приоритетов — кто кого перебивает

Наверху — «жизнь мирная», её перебивают всё более срочные планнеры. Кто применим и
приоритетнее — тот и рулит телом ПРЯМО СЕЙЧАС:

```
   СРОЧНОСТЬ
      ▲
      │  ┌────────────────────────────────────────────────┐
 выше │  │  anomaly_planner   ← стою в аномалии, надо выйти │  property_inside_anomaly
      │  ├────────────────────────────────────────────────┤
      │  │  danger_planner    ← граната/труп/удар          │  property_danger
      │  │                       прячусь / бегу от гранаты  │  property_danger_grenade
      │  ├────────────────────────────────────────────────┤
      │  │  combat_planner    ← есть враг → БОЙ             │  property_enemy = true
      │  │     (сюда мы вписали varka_search)               │
      │  ├────────────────────────────────────────────────┤
 ниже │  │  alife_planner     ← мирная жизнь: job, патруль, │  (база, работает
      │  │     охрана точки, костёр, разговор, сон...        │   когда врагов нет)
      │  └────────────────────────────────────────────────┘
      ▼
```

Мысль: **бой — не «режим», а просто планнер, который выиграл лестницу**, пока
`property_enemy = true`. Пропал враг (бит истёк) → combat отваливается → возвращается
alife → NPC топает обратно на свой post. Ты это видишь как «побегал и пошёл домой».

## Один тик планнера — псевдокод

```
   каждый кадр:
     1. пересчитать world-properties (видит врага? ранен? граната?)
     2. планнер ищет действие с макс. приоритетом, чьи preconditions выполнены
     3. если это действие != текущее → у старого finalize(), у нового initialize()
     4. execute() текущего действия  ← команды телу (см. файл 03)
```

Смена действия = `finalize` старого + `initialize` нового. (Наш `varka_search` в
`finalize` теперь отпускает лот — v0.16. Это тот же механизм.)

## Где сидит боевой выбор «C++ или скрипт»

Внутри `combat_planner` стоит развилка (`evaluator_check_combat`, ✓ грепнуто):

```
        property_enemy = true (есть враг)
                 │
                 ▼
        script_combat_type задан в logic-конфиге NPC?
           ╱                         ╲
        нет                          да
         │                            │
         ▼                            ▼
   ⚠️ C++-БОЙ движка         ✓ Lua-СХЕМА боя
   (наёмники, Долг,          combat_type =
    бандиты по умолчанию)      "camper"  → держит точку
                               "monolith"→ прёт на LKP
                               "zombied" → бредёт на LKP
```

`combat_type` — это поле в logic-секции NPC (ставит smart_terrain / скрипт квеста через
condlist). Нет поля → бой достаётся движку. **Это и есть наша будущая точка входа:**
свой `combat_type = "varka"` — и весь бой NPC идёт через нашу машину, а C++ молчит.

> **Октябрь 2026:** про `varka_search` в combat_planner выше — так было в июле. Своё действие со своим id в
> боевом подпланировщике роняло игру (движок кричит «враг убит» через switch без default по id действия);
> с v0.23 поиск живёт под ванильным id 34, остальные наши действия — в главном планировщике (PLANNER_MAP.md).
> Путь через `combat_type = "varka"` пока не пробовали.

## Что важно унести

- Планнер **не умный** — он таблица приоритетов над флагами. Вся «тактика» ванили —
  это какой планнер выиграл и какое действие внутри него сработало.
- **Один флаг `property_enemy`** зажигает весь бой. Гаснет бит памяти → гаснет флаг →
  бой кончился. Вот почему §НАБЛ 7.9 «тревога умирает раньше облака»: движок гасит флаг
  по своему таймеру, даже если по-хорошему искать ещё надо.
- Мы **не ломаем** планнер. Мы либо вставляем в него своё действие (как search), либо
  забираем весь бой через `combat_type`.
